# Mobile Pairing and Device Authentication Protocol

**Status:** security design contract for the Android companion  
**Scope:** one user, one LifeOS server, multiple revocable Android devices  
**Default deployment:** HTTPS over a trusted private network such as Tailscale

This protocol exists because the existing LifeOS HTTP API is designed for a
trusted single-user environment. A mobile client does not make that API safe to
expose publicly by itself.

## 1. Security goals

The mobile design provides:

- one independently revocable identity per Android installation;
- no provider API key on the phone;
- no reusable server administrator password in the app;
- short-lived access credentials;
- explicit operator-approved pairing;
- replay-resistant pairing;
- safe device loss/revocation;
- auditability without logging personal message bodies;
- compatibility with Android Keystore;
- a path to public-network access later without changing application semantics.

## 2. Non-goals

The first implementation does not:

- expose LifeOS directly to the public Internet;
- treat a Tailscale IP as the device identity;
- use a single shared bearer token across all phones;
- place Gmail/OpenAI/Anthropic credentials on Android;
- authenticate through browser cookies copied from another session;
- use Accessibility or VPN permissions for authentication;
- silently pair a device because it is on the same LAN.

## 3. Trust model

### Trusted operator session

Pairing starts from a LifeOS operator session that is already trusted by the
installation's existing deployment boundary.

### Untrusted new device

Before pairing, the Android application is untrusted even when it is physically
near the server or connected to the same network.

### Paired device

A paired device receives only the scopes granted to the Android companion. It
does not become a server administrator and does not receive provider secrets.

## 4. Key material

The Android companion generates a device key pair locally.

Recommended baseline:

- P-256 ECDSA if broad Android Keystore compatibility is the priority; or
- Ed25519 only where the supported Android API/Keystore matrix is verified.

The private key:

- is generated by Android Keystore;
- is non-exportable;
- never appears in SharedPreferences, logs, QR codes, or backup archives.

The server stores:

- device id;
- public key;
- display name;
- created/last-seen timestamps;
- status (active/revoked);
- granted scopes;
- optional app/version metadata;
- no private key.

## 5. Pairing flow

### Step 1 — operator creates a challenge

An authenticated operator requests a new pairing challenge.

Server creates:

```text
pairing_id
random_secret
expires_at
server_origin
server_instance_id
requested_scopes
```

Properties:

- at least 128 bits of cryptographic randomness;
- lifetime <= 5 minutes;
- single-use;
- stored server-side only as a hash where practical;
- invalidated after success, explicit cancellation, or expiry.

The operator sees a QR code or short transfer payload containing the public
pairing data and secret.

### Step 2 — device validates target

The Android app scans/receives the pairing payload and displays:

- LifeOS server origin;
- server/instance label;
- requested permissions;
- expiry.

The user must explicitly continue.

The application rejects:

- non-HTTPS origins except a separately enabled loopback/development mode;
- expired challenges;
- malformed origins;
- unexpected URL schemes;
- oversized payloads.

### Step 3 — device proves possession of its key

The Android app generates its device key pair and sends:

```json
{
  "pairing_id": "...",
  "pairing_secret": "...",
  "device_public_key": "...",
  "device_name": "...",
  "client_nonce": "..."
}
```

The server consumes the pairing challenge atomically and returns the device id
plus a server nonce/challenge.

The device signs a canonical challenge containing at least:

```text
protocol_version
server_instance_id
device_id
client_nonce
server_nonce
issued_at
```

The server verifies the signature before activating the device.

## 6. Session credentials

After pairing, possession of the device private key is the root device
credential.

A request session uses short-lived tokens rather than signing arbitrary API
payloads forever.

Suggested flow:

1. device requests a session challenge;
2. server sends nonce + expiry;
3. device signs the challenge;
4. server verifies active device + signature;
5. server mints a short-lived access token scoped to that device.

Access-token requirements:

- short lifetime (for example 10–30 minutes);
- contains device id and scopes;
- audience bound to the LifeOS API;
- rejected for revoked devices;
- refresh requires fresh proof of device-key possession.

Exact token format (opaque server session vs signed token) is an implementation
choice. Opaque server-side sessions are preferred initially because immediate
revocation and key rotation are simpler.

## 7. Scopes

The Android client does not receive one universal "everything" permission.

Initial scope groups:

- `chat.read`
- `chat.write`
- `tasks.read`
- `tasks.propose`
- `calendar.read`
- `calendar.propose`
- `notifications.receive`
- `voice.use`

High-impact server operations remain behind LifeOS's existing action policy and
confirmation gates even if a device has the corresponding transport scope.

A mobile scope authorizes access to the LifeOS action layer; it never overrides
tool-level authorization.

## 8. Request binding

Every authenticated mobile request records at least:

- device id;
- request id;
- route/action class;
- timestamp;
- outcome;
- authorization/confirmation decision.

Default logs exclude:

- email body;
- prompt body;
- contact names;
- note contents;
- attachment bytes;
- provider credentials.

Correlation IDs provide debugging without copying personal content into logs.

## 9. Replay and idempotency

Mutation requests use an operator-generated request id/idempotency key.

The server retains a bounded replay window per device. Repeating the same
mutation key resolves to the original outcome rather than performing the
mutation again.

Pairing and session nonces are single-use.

Clock skew is tolerated only within a documented small window; nonce uniqueness
remains the primary replay defense.

## 10. Device revocation

The operator can list paired devices and revoke one immediately.

Revocation:

1. marks the device inactive server-side;
2. invalidates active sessions;
3. rejects refresh/signature challenges from that device;
4. leaves audit metadata;
5. does not affect other devices.

The Android app deletes its local pairing metadata and Keystore alias when the
user selects "forget this server".

Device loss requires only server-side revocation; provider credentials do not
need rotation because they were never stored on the device.

## 11. Server identity and TLS

Phase 1 assumes HTTPS inside a trusted private network.

The client stores the canonical server origin after pairing. It does not follow
authentication requests to arbitrary origins.

If certificate pinning is introduced later, the design must include deliberate
certificate rotation/recovery. Pinning is not added merely as a checkbox.

Public-Internet deployment remains disabled until:

- mobile authentication is implemented;
- rate limiting exists;
- pairing brute-force controls exist;
- origin/CORS/CSRF boundaries are documented and tested;
- security headers are configured;
- server endpoints are audited for mobile scopes.

## 12. Android storage

Store in Android Keystore:

- device private key;
- any local encryption key protecting opaque refresh/session material.

Store in app-private preferences/database:

- device id;
- server origin;
- public metadata;
- non-secret UI preferences.

Exclude credentials and offline sensitive queues from Android cloud backup
unless the backup design explicitly encrypts and binds them to a recoverable
identity.

## 13. Biometric/user-presence policy

Pairing always requires explicit user interaction.

Optional biometric/device-credential confirmation may be required for:

- enabling new high-impact scopes;
- sending a confirmed email;
- destructive calendar/task operations;
- revealing especially sensitive local content.

Biometrics are an authorization factor for an action; they are not sent to the
server and are not a substitute for server-side policy.

## 14. Offline queue

Offline Android actions are proposals.

Each queued proposal records:

```text
proposal_id
created_at
server_revision_or_sync_cursor
canonical_action
canonical_arguments
confirmation_state
idempotency_key
```

On reconnect the server:

1. revalidates device/session;
2. checks current state;
3. detects conflicts/stale assumptions;
4. reapplies action policy;
5. requests renewed confirmation if the action or target changed;
6. commits at most once.

A confirmation captured for one canonical action cannot authorize a modified
action after reconciliation.

## 15. Threat cases and required negative tests

The implementation is incomplete until tests cover:

- expired pairing secret;
- reused pairing secret;
- wrong device signature;
- malformed/oversized QR payload;
- server-origin substitution;
- replayed session challenge;
- replayed mutation request;
- revoked device;
- token for wrong audience/device;
- missing scope;
- scope present but LifeOS action policy denies the mutation;
- offline proposal whose target changed;
- device reinstall with old server registration;
- concurrent pairing attempts;
- brute-force throttling;
- log redaction;
- process death between challenge and activation.

## 16. Rollout gates

### Gate A — private-network read-only client

- pairing implemented;
- device revocation implemented;
- chat/calendar/task reads only;
- Tailscale/HTTPS required.

### Gate B — proposed mutations

- idempotency implemented;
- confirmation binding implemented;
- task/calendar proposals supported;
- negative authorization tests green.

### Gate C — voice and background features

- Android foreground-service policy verified;
- native wake-word pipeline reviewed;
- notification privacy reviewed;
- single-use voice confirmation integrated.

### Gate D — public-network option

Only after a separate security review and external-style penetration test of
the mobile authentication boundary.

## 17. Upstream contribution shape

If proposed to LifeOS upstream, mobile authentication is split from the Android
UI:

1. generic device-pairing/authentication server primitives;
2. device management/revocation UI;
3. Android companion as a separate follow-up.

This keeps the security boundary reviewable without asking maintainers to
review an entire mobile application at the same time.
