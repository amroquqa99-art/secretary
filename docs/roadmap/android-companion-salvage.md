# Android Companion Salvage Review

**Source reviewed:** `archive/pre-lifeos-2026-10-07`  
**Target architecture:** LifeOS server + Android companion  
**Status:** design decision; no legacy Android code is merged into LifeOS by this document.

The archived Secretary application contains useful Android-specific work, but
its code is not imported wholesale. LifeOS remains the server, knowledge,
search, agent, and integration authority. The Android application is a narrow
companion for device-local capabilities.

## 1. Decision summary

| Legacy area | Decision | Reason |
|---|---|---|
| Android Keystore secret storage | Reuse concept; rewrite and test | Correct platform boundary, small surface |
| Encrypted backup/restore | Reuse design ideas; do not copy wholesale | Strong validation ideas, but schema is legacy-specific |
| Single-use voice confirmation | Reuse protocol concept | Valuable safety primitive for dangerous voice actions |
| Deterministic planning logic | Port semantics selectively | Useful offline fallback, but LifeOS owns canonical tasks/calendar |
| Accessibility app blocking | Do not ship by default | High-permission, UX/policy/security risk |
| DNS VPN focus blocking | Do not copy as-is | Network security/TLS/DNS correctness requires a dedicated design |
| Old Room/SQLite life schema | Do not merge | Competes with LifeOS data model and creates dual authority |
| Legacy local assistant/router | Do not merge wholesale | Provider/agent orchestration now belongs to LifeOS |

## 2. Keystore secret storage

The archived `SecretStore.kt` uses Android Keystore with AES-256-GCM and keeps
ciphertext in private SharedPreferences. That is directionally correct for
device credentials.

The companion implementation should preserve these properties:

- key material never leaves Android Keystore;
- one key alias belongs to one application installation/profile;
- AES-GCM uses a fresh nonce generated by the platform;
- plaintext secrets are never logged;
- corruption/decryption failure is explicit rather than silently interpreted as
  an absent credential;
- credential deletion removes both application metadata and, when appropriate,
  the related Keystore alias;
- device pairing credentials are independent from OpenAI/provider API keys;
- server-side revocation remains authoritative.

The legacy implementation should not be copied verbatim because the new
credential type, migration story, biometric policy, backup exclusion, and
revocation contract differ.

## 3. Backup and restore

The archived `BackupManager.kt` contains several practices worth keeping:

- encrypted export;
- bounded input sizes;
- zip-entry allow-listing;
- duplicate-entry rejection;
- schema validation;
- rollback copy before restore;
- transactional database replacement;
- validation before commit;
- cancellation of pending assistant actions after restore.

These are good invariants.

The legacy exporter is coupled to Secretary's old tables and URIs, so it is not
the LifeOS backup format. The companion should primarily back up device-local
state such as pairing metadata, offline capture queues, local preferences, and
optional on-device model configuration. Canonical LifeOS server data follows
LifeOS's own backup/export path.

Future mobile restore must reject:

- path traversal;
- duplicate entries;
- unknown schema versions;
- oversized decompressed content;
- unknown action/tool payloads;
- credentials imported into the wrong device identity;
- stale pending destructive actions.

## 4. Voice confirmation

`VoiceConfirmation.kt` has a strong safety property: confirmation is volatile,
single-use, expires quickly, and is bound to the exact proposed call.

That contract should be retained and generalized:

```
proposal_id
tool_name
canonical_arguments_hash
issued_at
expires_at
single_use = true
```

A spoken confirmation authorizes exactly one pending proposal. It must not
authorize a different tool call, a modified recipient/time/path, or a later
proposal.

For high-impact actions, voice confirmation alone is not automatically
sufficient. The policy engine may require device unlock, biometric confirmation,
or an in-app confirmation sheet.

## 5. Offline planning

The archived `AssistantPlanning.kt` demonstrates a useful deterministic
fallback:

- validates dependency graphs;
- respects fixed calendar blocks;
- uses explicit working windows;
- keeps already-scheduled tasks from being duplicated;
- orders by priority and deadline;
- marks assumed durations;
- reports tasks that could not be scheduled.

The new companion can reuse those semantics for **offline proposals**, not
canonical writes.

Rule:

> Offline planning may create a proposed schedule in the local queue. LifeOS
> remains authoritative for final calendar/task mutations when connectivity
> returns.

Conflict resolution must compare the server revision seen when the proposal was
created with the current server revision before applying it.

## 6. Accessibility blocking

The archived accessibility service can push the user home when a blocked app
opens. It is effective but carries broad observation capability.

It is excluded from the initial companion because:

- Accessibility is a high-trust Android permission;
- platform/store policy scrutiny is significant;
- package/window observation creates privacy implications;
- incorrect matching can make the device frustrating or inaccessible;
- this feature is unrelated to the minimum viable LifeOS Android client.

If reintroduced, it lives behind an optional Focus extension with:

- explicit opt-in;
- narrow package allow/block lists;
- no captured content;
- no network transmission of accessibility events;
- an emergency disable path;
- instrumentation tests for lock-out recovery.

## 7. DNS/VPN blocking

The archived VPN design routes DNS traffic into a local tunnel and forwards
allowed DNS-over-HTTPS requests. The idea is useful for Strict Mode but is not
copied as-is.

A production implementation requires a separate threat model for:

- IPv4 and IPv6;
- TCP and UDP DNS;
- DNS-over-HTTPS/DNS-over-TLS bypass;
- VPN coexistence;
- captive portals;
- DNSSEC/response validation expectations;
- tunnel lifecycle and crash recovery;
- battery cost;
- fail-open versus fail-closed behavior;
- endpoint pinning/trust strategy;
- Android version differences.

This feature is deferred until the core companion is stable.

## 8. Companion boundaries

### Companion owns

- pairing UI and device credential;
- secure local credential storage;
- Android notifications;
- microphone/audio session integration;
- optional native wake-word engine;
- offline capture/proposal queue;
- device-level connectivity state;
- optional on-device inference profile;
- optional Focus extensions.

### LifeOS server owns

- canonical tasks and schedules;
- Gmail/calendar/contacts integrations;
- vault and memory;
- embeddings/search/indexes;
- people/CRM graph;
- agent orchestration;
- provider credentials for server-side models;
- audit trail for server mutations.

There is one canonical owner per piece of state.

## 9. Initial Android protocol

The first native companion does not expose LifeOS publicly.

Connection assumptions:

1. The phone and LifeOS server communicate over HTTPS on a trusted private
   network such as Tailscale.
2. The user initiates pairing from an already trusted LifeOS session.
3. The server creates a short-lived pairing challenge.
4. The device creates/stores its own credential in Android Keystore.
5. The server records a revocable device identity.
6. Every mobile request is attributable to one paired device.
7. Removing the device server-side invalidates future requests.

The public-Internet auth protocol remains a later security phase.

## 10. Required tests before implementation is called complete

- Keystore round-trip and corruption failure;
- credential revocation;
- reinstall/new-device behavior;
- pairing expiration and replay rejection;
- offline queue idempotency;
- task/calendar conflict detection;
- exact-action voice confirmation;
- Android process-death recovery;
- network-loss recovery;
- Arabic/English notification and voice text;
- no secret or message body in default logs;
- no Accessibility or VPN permission in the base companion manifest.

## 11. What is preserved from the old project

The old implementation remains permanently inspectable at:

```
archive/pre-lifeos-2026-10-07
```

Useful code can be ported through focused PRs with tests and review. The archive
is a reference and rollback point, not a second source tree to merge wholesale.
